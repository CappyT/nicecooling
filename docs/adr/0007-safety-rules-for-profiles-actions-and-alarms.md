# Safety rules between Profiles, Actions, the pump and alarm actions

Profiles, Actions, the Pump floor and alarm actions each make sense alone but conflict on a real loop. We fix four rules:

- **Profile activation writes the Leakshield in any Mode.** A Profile activation writes the Leakshield also while an Action runs or the Mode is RELEASE, as aquasuite does. The owner accepted the risk that a Rule group writes SHIELD on an open loop.
- **Refill starts in any pump state.** The Leakshield manual requires the pump off during Refill, but the Pump floor and the pump-stop Alarm keep the pump on. The daemon starts a Refill whatever the pump does. The app warns before it sends the Refill while a Pump channel of the Loop reads above 0 rpm or has no tach value. The user decides.
- **The daemon handles leaks.** The daemon's alarm responses, with their cancellable delay, handle leak Alarms. The signal output Device response stays as a backup only for the system Alarm, as a long press, for the case where Linux is hung. The key-sequence Device response stays off, because the Leakshield types it into the focused window, a terminal included. nicecooling proposes these device settings and warns when they overlap; it does not write them on its own.
- **No action needs a password.** nicecooling warns and never refuses a choice of the user to protect the user. A local, active member of `wheel` does not enter a password for any polkit action, `critical` included: setting RELEASE directly, saving a Profile with Mode RELEASE, restoring a backup and a factory reset. The polkit dialog shows only for a user outside `wheel`. The owner accepted this risk.
